# Tech Stack

Stakeholder requirements: modern TypeScript on the frontend, latest .NET on the backend, one backend shared by all clients, able to handle at least 10 live requests per second initially, up to 50 at peak close to exams, and to grow from there. Most code is written test-first (TDD).

Items marked **Proposed** were not decided by stakeholders. They are sensible defaults and can be changed before the phase that first uses them.

## Development practice: TDD

Most of Kotsu's code is written test-first. This is **Decided**.

- **Red, green, refactor.** Write a failing test, write the least code that passes it, then tidy up with the tests green.
- **Tests come first in every phase.** A roadmap phase starts by turning its "Done when" into failing tests, and is finished when they pass.
- **Strict where logic lives.** The scheduling engine, API endpoints, data access and client logic (hooks, state, API calls, form validation) are always test-first.
- **Arrange, Act, Assert.** Every test, backend and client, follows the Arrange, Act, Assert pattern. The three sections appear in that order and are marked with `// Arrange`, `// Act` and `// Assert` comments. Each test has one Act. A section with nothing in it can be left out, for example a test with no setup.
- **Tests and lint run in CI.** GitHub Actions runs both on every pull request, and a pull request cannot merge while either fails.

"Most" has stated exceptions, where a test written first adds little:

- Generated code, such as the TypeScript API client and EF Core migrations.
- Configuration, build and deployment scripts.
- Visual styling and layout. Behaviour of a screen is tested; how it looks is reviewed by eye.
- Throwaway spikes, which are deleted and rebuilt test-first once the approach is known.

## Scalability

| Load | Target | Status |
| --- | --- | --- |
| Normal | At least 10 live requests per second, sustained | Decided |
| Peak (close to exams) | Up to 50 requests per second | Decided |

Both figures are small for ASP.NET Core and PostgreSQL, so the launch architecture is deliberately simple. It is sized for the peak, not the normal load:

| Concern | Launch architecture | Status |
| --- | --- | --- |
| API | Two small instances behind a load balancer, with autoscaling allowed to add a few more in exam season. | Proposed |
| Database | One PostgreSQL instance with automated backups, sized for the peak. No read replicas. | Proposed |
| Database connections | Connection pooling, with the pool sized so that the maximum number of API instances cannot exhaust PostgreSQL's connections. | Proposed |
| Caching | HTTP cache headers on board, exam and syllabus content. No separate cache server. | Proposed |
| Autoscaling | On, with a low upper limit. It covers the exam-season peak and caps the cost. | Proposed |
| Response time | 95% of requests answered within 500 ms, at both normal and peak load | Decided |

Both targets are proven by a load test, not assumed (see [roadmap.md](roadmap.md)).

Growth beyond the peak target must not need a redesign, so these rules hold from the first line of code:

- **Stateless API.** No in-memory session state, so instances can be added behind the load balancer.
- **Read-heavy content is cacheable.** Boards, exams and syllabus content change rarely, so they can move to a CDN when load calls for it.
- **Schedules are computed, not looked up.** The engine is a pure function, so it scales with API instances and needs no shared state. It schedules multiple subjects at once: selected topics across the student's subjects, placed inside a 1–4 week window, sharing the weekly hours.
- **Containers.** The API ships as a container image, so it is not tied to one Azure hosting service and runs with or without autoscaling.

## Expanding beyond Great Britain

Kotsu launches in Great Britain only and expands to other countries later. To keep that cheap:

- **Country is data, not code.** Each country defines its own stages, subjects and boards as content (for example SQA National 5 and Highers next to GCSE and A-level), not hard-coded types. No KS-specific enum. A board is chosen only where a country has several (England); Scotland and Wales have one each.
- **Text is translatable.** Client strings go through an i18n library from the first screen, with British English as the only language at launch (**Proposed**).
- **Dates and times are locale-aware.** Stored in UTC, schedule windows as calendar dates, formatted on the client.
- **Data residency.** Personal data is hosted in an Azure UK region at launch (**Proposed**).
